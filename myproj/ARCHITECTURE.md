## Данные и сохранение

- Main process читает и записывает JSON по пути `path.join(app.getPath('userData'), 'assist-data.json')`.
- В коде вызывается `app.setName('Assist')`; на Windows путь userData обычно привязан к профилю пользователя и имени приложения. Точный путь установленного экземпляра нужно смотреть в его окружении, не подменяя его старым предположением `%APPDATA%\\assist-overlay`.
- В JSON лежат настройки, темы/источники и история. API-ключи при доступном `safeStorage` шифруются; при переносе данных в другой контекст Windows расшифровка может не сработать.
- JSON import/export базы знаний — отдельный переносимый формат. Экспорт источников не переносит настройки API/секреты и историю чата.

## Путь вопроса в текущем коде

1. `renderer.js` добавляет вопрос в очередь и показывает `…`.
2. Вопрос может объединиться с предыдущим, если похож на короткое продолжение.
3. `splitQuestionParts` делит многочастный вопрос (до четырёх частей); тип RP/ситуации определяется в основном локальными правилами/регулярными выражениями.
4. ИИ-путь выполняет отбор по включённым источникам двумя методами: `searchQuestion(..., relaxed: true)` и `directSearchMatches(...)`. Поиск кандидатов просматривает все включённые источники; модели передаются до 9 фрагментов с бюджетом 15 000 символов. Слишком длинный фрагмент помечается как сокращённый.
5. Выбранные фрагменты получают метки `[F#]`; архивные материалы — `[A#]`. Модель получает роль, пожелания, общие правила ответа и найденный контекст.
6. `main.js` отправляет запрос на OpenAI Chat Completions, OpenAI Responses или Gemini. OpenAI-совместимые пути запрашиваются с потоковым выводом. `reasoning_effort: low` добавляется только для распознанных reasoning-моделей и поддерживаемых API-путей; для них не передаётся `temperature`. Лимит генерации — 700 токенов для краткого режима и 1800 для полного.
7. Потоковый текст поступает через IPC. Renderer убирает маркер `[DATA_INSUFFICIENT]`, но сохраняет уже найденную часть ответа; если не найдено ничего — показывает короткое сообщение. Ссылки на источники показываются только для меток, присутствующих в ответе. Обрезка по лимиту модели сопровождается предупреждением.
8. Полное время последнего ответа показывается в `latLabel` в шапке. Детали могут показываться в диагностике при включённом debugRetrieval.

### Как устроен поиск

- Источники делятся на блоки по заголовкам и длине; для блока кэшируются слова и вектор частот терминов.
- Обычный поиск использует BM25-подобное ранжирование, частотность, покрытие ключевых слов, заголовки, резервы по редким словам/темам и соседние блоки.
- Дополнительный `directSearchMatches` объединяет лексический score, cosine similarity частотных векторов слов и вес заголовков. Это локальная математическая близость слов, а не нейросетевые embeddings и не понимание произвольных перефразов.
- Старое поле `searchDictionary` удаляется при миграции и больше не участвует в поиске или экспорте. В `searchSynonyms` остаются только общие связи терминов; доменные игровые алиасы удалены. Совпадение по префиксу включается только для достаточно длинных слов.
- Обработка поиска выполняется в renderer. Web Worker/Node Worker в `main.js` и `renderer.js` не найден.

## Оверлей и аудио

- Main process создаёт окно Electron поверх других окон, настраивает режим пропуска кликов, фокусируемость, бинды и скрытие с панели задач.
- Глобальные клавиатурные/мышиные бинды обрабатывает `uiohook-napi`.
- В голосовом вводе возможны микрофон, системный loopback или их сочетание. Установленный `loopback-capture` 3.0.2 отдаёт 16-bit PCM, stereo, 48 kHz; в renderer формат преобразуется в mono 16 kHz для Yandex SpeechKit. Проверку устройства нельзя запускать одновременно с распознаванием.
- Yandex SpeechKit синхронно принимает WAV и имеет таймаут одного запроса 30 секунд; на HTTP 500/502/503/504 выполняется один повтор после 700 мс. Это ограниченная обработка временных серверных ошибок, не гарантия успешного распознавания.
- Нельзя считать, что «игра никогда не теряет фокус» гарантировано одним только описанием архитектуры: это нужно подтверждать на целевой игре и собранном exe.

## Сборка

- `npm start` запускает исходное приложение через Electron.
- `npm run dist` и `npm run dist:portable` определены в `package.json`.
- electron-builder включает явный список файлов, `asar: true`, распаковывает некоторые native modules и добавляет PowerShell-скрипт как extra resource.
- Сам факт наличия скриптов сборки не подтверждает, что конкретный `.exe` собран из текущего HEAD или проверен запуском.

## Риски/ограничения, видимые в коде

1. Поиск и разбор контекста выполняются в renderer, не в Worker; большая база потенциально блокирует интерфейс. Токены блоков кэшируются, а редакторы источников создаются только для раскрытых тем.
2. Восприятие ситуации/RP частично зависит от регулярных выражений, поэтому неоднозначная формулировка может выбрать неверную ветку.
3. Поиск может собрать до 30 групп и 40 000 символов кандидатов, но запрос модели ограничен 9 фрагментами и 15 000 символами. Этот компромисс оставлен ради скорости; кандидат, не попавший в контекст, модель не увидит.
4. Повторы возможны при сетевых/HTTP-ошибках и совместимости параметров; «ровно один вызов» не является абсолютной гарантией.
5. Тестовые файлы содержат примеры и ожидаемые ответы; они не являются фактической базой пользовательских источников.
