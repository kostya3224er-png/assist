# Принятые продуктовые решения

Этот журнал фиксирует пожелания владельца и устойчивые решения из переписки. Он не подтверждает, что реализация уже соответствует решению; см. `STATUS.md`.

## Продукт и данные

- Assist остаётся универсальным оверлеем: нельзя встраивать в код нормы конкретной игры, сервера, организации или роли.
- Роль и пользовательские пожелания задаются настройками. Факты проекта находятся в источниках.
- Пользователь сам выбирает нужные темы и источники; ИИ должен использовать включённые источники и не подтягивать отключённые.
- Отдельный верхний поиск остаётся самостоятельной функцией без участия модели. Не переделывать его без конкретной причины и просьбы.
- Словари поиска не должны загромождать UI. Автоматическая нормализация допустима, но обнаруженную вручную связь терминов нельзя считать обязательным правилом для любой базы.
- Архивные/исторические нормы не выдаются за действующие. Если вопрос именно об истории изменений, архив можно использовать с датами.

## Ответы

- Справочный ответ должен быть быстрым, прямым и подтверждённым источниками; перечислять нужные условия/исключения, а не ссылаться на список без самого списка.
- Если вопрос состоит из частей, отвечать отдельно по каждой части; нехватку данных по одной части не превращать в отказ от всего ответа.
- Для ситуации/RP нужна готовая задача/действие в настроенной роли. Источники ограничивают выдуманные нормы, но отсутствие готового сценария не должно само по себе вызывать отказ.
- RP-детали задаёт текущий запрос и проект пользователя, не зашивать примеры ПД в общий продукт.
- Ссылки `[F#]`/[`A#`] допустимы только на действительно переданные фрагменты.
- В чате не показывать отдельные карточки найденных фрагментов и миллисекунды. Время последнего ответа держать в шапке; подробную диагностику — только в debug.
- Модель не должна иметь искусственный короткий жёсткий таймаут, который обрывает допустимый ответ. Пользователь может остановить запрос вручную; сетевые ошибки обрабатываются отдельно.
- Предпочтительный режим рассуждения — `low`, без отдельной настройки в пользовательском интерфейсе. Это пожелание пользователя, а не подтверждение, что оно уже применено в текущем коде.
- При временных сетевых ошибках нужен автоматический повтор. Не повторять заведомо неисправимые ошибки авторизации и явные отказы оплаты/квоты. Универсально проверить остаток баланса до повтора может быть невозможно; решение должно опираться на ответ провайдера и не обещать недоступную проверку баланса.

## Производительность и UX

- Приоритет: повысить точность отбора для AI без поломки самостоятельного поиска.
- Избегать лишних вызовов модели; один нормальный путь — один вызов, кроме явно обоснованных повторов при сетевых ошибках/несовместимости параметров.
- Ответ должен быть потоковым, если провайдер поддерживает; время показывается по фактическому завершению.
- Оверлей не должен останавливать игру, перехватывать фокус без необходимости или блокировать ввод в своих полях.
- Не добавлять в UI вспомогательные блоки/карточки/настройки без запроса и понятной пользы пользователю.

## Сборка и данные пользователя

- При создании exe сначала сохранить пользовательские источники и настройки; не подменять и не удалять `assist-data.json`.
- Код приложения и пользовательские данные — разные артефакты. Перенос exe сам по себе не переносит профиль приложения.
- Не записывать API-ключи, личные логи или большую пользовательскую базу в проектную документацию/архив контекста.
- Перед сборкой сверять package/build configuration, не менять код, если запрос только на сборку.

## Документация проекта

- Markdown-файлы помогают переносить контекст между Codex, ChatGPT и Claude, но не обязательны для работы Assist и сами по себе не улучшают приложение.
- Не требуется заполнять все шаблоны или поддерживать большой набор заметок. Достаточно обновлять ключевые документы, когда меняются подтверждённые факты или устойчивые решения.
- Технические сведения сверяются с локальным кодом прежде всего в Codex; ChatGPT и Claude перепроверяют их по актуальным исходникам, доступным в конкретной задаче.
- Когда пользователь говорит, что «структура не нужна», имеется в виду структура Markdown-документов проекта; это не решение об удалении поисковых словарей из приложения.

## Решения, требующие подтверждения кодом перед заявлениями

- Поиск «≤150 мс», ответы «≈3 секунды», CPU/GPU в простое и отсутствие потери фокуса — цели/исторические замеры, не гарантии.
- Утверждения, что модель всегда делает один запрос или сама «понимает всю базу», нельзя повторять без трассировки конкретного вопроса.
- «Семантический поиск» в текущем коде — не модель embeddings; не обещать поиск смысловых перефразов как гарантированную возможность.
